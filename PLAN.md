## 2. Авторизация через maddy (IMAP) — подтверждено сервером

**Факты с сервера (2026-11-05):** Debian 12 (kernel 6.1.190-1), maddy **0.8.2** (go1.25.5), state_dir `/var/lib/maddy`. **Прецедент:** files.xor.world уже авторизуется именно так — PHP `imap_open("{127.0.0.1:993/imap/ssl/novalidate-cert}INBOX", user, pass)`, при неудаче `sleep(15)` как анти-брутфорс. Значит: 993 слушает loopback, TLS принимает соединение без валидации сертификата, логин-идентификатор maddy принимает как есть.

maddy **не отдаёт HTTP-auth API**. Проверенные варианты:

| Вариант | Суть | Вердикт |
|---|---|---|
| **A. IMAP LOGIN probe (рекомендую)** | Приложение коннектится к maddy на 127.0.0.1:993 (implicit TLS), `LOGIN admin@example.org <pass>`, ждёт OK/NO, `LOGOUT`. maddy сам сверяет argon2-хэш из pass_table (SQLite `credentials.db`). | Ноль изменений в maddy; тот же путь, что у проверенного files.xor.world. Argon2 намеренно медленный (~50–200 мс) — при 50 пользователях не проблема. |
| B. Читать `credentials.db` напрямую | Тот же SQLite, хэши argon2id. | Хрупко (формат/права/блокировки), не стоит. |
| C. NetAuth / PAM | Отдельная подсистема. | Overkill для 50 юзеров. |

Детали варианта A (реализация в .NET):
- **Прецедент №2: собственный скрипт админа `maddy_add_mbox.sh` уже делает ровно этот probe** (`printf "A1 LOGIN ... A2 LOGOUT" | openssl s_client -connect localhost:993` + grep `OK .* LOGIN completed`). Метод не просто валиден — он уже эксплуатируется на этом сервере.
- CLI maddy 0.8.2: **`maddy creds create --password PASS EMAIL` / `maddy imap-acct create`** (не `maddyctl` — его в 0.8.2 нет).
- Логин = **полный email** — подтверждено скриптом (`LOGIN $EMAIL`), auth_map в maddy.conf не настроен (в grep не попал) → дефолт «email как идентификатор».
- Библиотека: **MailKit** — `ImapClient.Connect("127.0.0.1", 993, SecureSocketOptions.SslOnConnect)` + `ServerCertificateValidationCallback = accept-all` (только для loopback — аналог `novalidate-cert` в PHP). Если MailKit не захочется — голый `SslStream` + 3 строки IMAP (`LOGIN`/`OK|NO`/`LOGOUT`), протокол там тривиальный.
- **Сессии**: серверные (in-memory + запись на диск для переживания рестарта), cookie `HttpOnly; Secure; SameSite=Lax; Max-Age=30д`. Никаких токенов в localStorage.
- **CSRF**: SameSite=Lax + double-submit-токен на мутающих POST.
- **Брутфорс**: nginx `limit_req zone=login burst=3 nodelay` на `/api/login` + в приложении задержка ~5–15 с на неудачу (конвенция сервера: `sleep(15)` в files.xor.world) + бэкофф по (ip, login). IMAP-probe идёт по loopback — наружу пароль не уходит.
- Пароль нигде не хранится: maddy — единственный источник истины. Смена пароля = смена в maddy (на сервере уже есть `maddy_set_password.sh`).
- Выход сессии при смене пароля в maddy не отслеживаем (принято: TTL 30 дней).

## 3. Регистрация и лимит 50 пользователей (решено: само-регистрация)

- **Регистрация = первый успешный вход.** Успешный IMAP-probe против maddy для адреса `@xor.world` → если каталога `users/<uid>/` нет, он создаётся автоматически. Отдельного allowlist нет; фильтр «свой/чужой» — сам maddy (чужого пароль не примет) + доменное ограничение `@xor.world`.
- **Лимит 50 = счётчик каталогов в `users/`.** При входе нового (первого для себя) пользователя, если каталогов уже ≥50 — отказ «сервер заполнен» (существующим пользователям вход разрешён всегда). Проверка под lock'ом создания, чтобы не было гонки.
- Защита от «раздувания» каталогов: каталог создаётся только после успешного IMAP-логина, брутфорс и так rate-limited — мусорные каталоги не появятся.
- Профили грузятся лениво (LRU, кэш ~20 самых свежих в RAM, остальные с диска по первому запросу). Модель НН на юзера — десятки КБ, 50 юзеров — мегабайты, не проблема.

## 5. Многопользовательская адаптация функционала

- Все пути API работают в контексте юзера из сессии; uid **никогда** не берётся из тела запроса.
- Глобальный `lock(Sync)` → per-user lock (словарь по uid).
- Фоновые задачи (train_ga, tune, validate, backfill) — per-user очередь (`/api/job` уже асинхронный, семантика та же, но job'ы изолированы по юзеру); **на сервере (2 vCPU) — максимум 1 job одновременно**, остальные в очереди.
- Погода/Kp: live-кэш общий по (округлённые lat/lon), архивные запросы — общий кэш на сервере (open-meteo/GFZ/NOAA — все юзеры делят, экономия трафика сервера).
- **Локация — по названию населённого пункта, не координатам** (решение владельца): в конфиге юзера поле «Населённый пункт» (текст). При сохранении сервер один раз геокодирует (Nominatim/OSM, User-Agent + ≤1 req/s, результат в общий кэш `/opt/bpdata/geo-cache.json`) и кладёт resolved lat/lon рядом с названием — дальнейшая погода ходит по закешированным координатам, повторного геокодинга нет. Ручной override координат — в «дополнительно». Понятность пользователю: «Ижевск» вместо «56.85,53.21».
- **Приватность конфигов**: настройки юзера (включая локацию, лекарства, будильники) видят только он; ни один эндпоинт не отдаёт данные чужого профиля; нет списков пользователей, поиска по людям, агрегатов между юзерами.
- Журнал правок: append-only формат уже позволяет «кто/когда» — в вебе добавляем поле editor (для будущего разделения доступа «семейный доступ», не в v1).

## 6. Будильники — метод срабатывания (главный вопрос)

В десктопе: Forms.Timer + NAudio + балюн. В вебе браузер сам ничего не «помнит», если вкладка закрыта. Схема — **гибрид из трёх каналов**:

1. **Web Push (основной)** — работает при закрытой вкладке:
   - VAPID-ключи генерируются один раз на сервере; SPA регистрирует service worker, подписку шлёт на сервер (`POST /api/push/subscribe`).
   - Серверный планировщик (один `IHostedService`-таймер, тик раз в 30 с) по конфигам всех юзеров считает срабатывания: те же режимы daily / days(ISO) / everyN(Anchor) + **окно догона 30 мин**, вычисление в таймзоне юзера (tz хранится в профиле, берётся из браузера при первом входе).
   - Push-библиотека на .NET: `WebPush` (NuGet) — шлёт на Mozilla autopush / FCM без ключей Google.
   - Ограничение: **кастомный звук в push-уведомлении невозможен** — service worker не может воспроизводить аудио (нет DOM/Audio), а `showNotification` не принимает свой звук: играет системный звук ОС/браузера. Можно лишь `renotify: true` + `vibrate` для повторяемости. alarm.mp3 поэтому живёт только в канале 2 (открытая вкладка).
   - iOS: web push только у PWA, добавленной на домашний экран — задокументировать в UI.
2. **Вкладка открыта → локальный таймер + alarm.mp3** (как в десктопе): **текущий `alarm.mp3` (62 КБ) переиспользуется как есть** — браузеры умеют mp3 нативно; раздаётся статикой, кэшируется service worker'ом (62 КБ — ничтожно, в трафик не влияет). SPA при каждом рендере проверяет локальное время против расписания (та же логика CheckAlarms на клиенте), при попадании в окно — `<audio loop>` с alarm.mp3 + баннер «Стоп». **Политика autoplay**: браузер разрешает звук только после пользовательского жеста на странице — снимается «разблокировкой» audio на первом клике после логина (постановка `audio.play()` на muted-источнике в обработчике любого клика); на практике пользователь, вошедший и работающий со страницей, уже взаимодействовал. Кнопка «Стоп» в уведомлении push (`actions:[{action:'stop'}]`) → POST на сервер → отметка «погашено», вкладки больше не звенят (состояние «dismissed» на сервере, SPA сверяется).
3. **Email-фолбэк (опция per-user)**: сработал будильник, push-доставка не подтверждена → письмо «Пора измерить АД» через локальный maddy submission на ящик юзера. Latency секунды–минуты, но доставляется всегда.

Надёжность: сервер упал/перезапустился — после старта планировщик догоняет пропущенные срабатывания за последние 30 мин (та же семантика догона). Дубли push подавляются записью `LastFired` в профиль юзера (persist).

## 7. Уменьшение трафика клиент↔сервер

Болезненные точки текущего BPMonitor: `GET /api/state` = полный снимок (конфиг + **все** измерения + веса НН + погода) на каждый запрос; SPA опрашивает его регулярно.

План (по убыванию эффекта):
1. **Дельта-синхронизация вместо полного state.** `data.bin` append-only с естественным seq → клиент хранит `lastSeq`; `GET /api/delta?since=seq` возвращает только дописанные записи + тумстоуны + изменённый конфиг (конфиг — по revision-счётчику). 304/пусто в устойчивом состоянии ≈ **сотни байт** вместо десятков КБ.
2. **ETag на всё** (`/api/state`, `/api/delta`, SPA) + `If-None-Match` → 304 без тела.
3. **nginx: gzip** (или brotli, если модуль доступен — см. ⚠ в §8) для JSON/HTML/JS + **HTTP/2** (`listen ... ssl http2` на nginx 1.22). JSON НН/измеримых сжимается в 5–8 раз.
4. **История — пагинация**: `/api/measurements?from&to&limit` (в кладке «История» грузим окном, не всё).
5. **Веса НН — по версии модели**: `nn.version` растёт при Train/SaveNn; клиент кэширует веса, получает их только при изменении.
6. **Погода — серверный кэш + дельта**: live-погода меняется раз в PollMin; клиент получает её только при изменении (rev в дельте).
7. **Polling → SSE** (`GET /api/events`): сервер сам толкает дельту (изменения юзера, прогноз, будильник-стоп). Fallback на long-poll. Частота фоновых запросов падает с «каждые N сек» до нуля.
8. Статика: один `index.html` + `alarm.mp3`, service worker кэширует со hash-busting.

Ожидаемо: steady-state < 1 КБ/мин на юзера против текущих ~50–100 КБ на опрос.

## 8. nginx / развёртывание

> ⚠ Debian 12 = nginx 1.22.1: directive `http2 on;` does not exist (1.25+). Use `listen 443 ssl http2;`. Brotli: install `libnginx-mod-http-brotli-filter` + `libnginx-mod-http-brotli-static` (есть в репо Debian 12, проверено).

```
server {
  server_name bp.xor.world;
  listen 443 ssl http2;        # nginx 1.22 syntax (Debian 12)
  # certbot --nginx
  client_max_body_size 20m;              # импорт export/all
  location /api/login { limit_req zone=login burst=3 nodelay; proxy_pass ...; }
  location / { proxy_pass http://127.0.0.1:8090;
               proxy_http_version 1.1; proxy_set_header Connection "";
               # SSE: proxy_buffering off; для /api/events
             }
}
```
- systemd: `bpxor.service`, `Restart=always`, отдельный пользователь `bpxor`, `ReadWritePaths=/opt/bpdata` (данные в /opt, не в StateDirectory — по решению владельца).
- Бэкапы: суточный zip на юзера (переиспользуем логику `backups/yyyyMMdd.zip`, keep 30) + общий `tar /opt/bpdata` cron-ом.
- Логи: journald + per-user файловый лог (ротация 5 МБ, как в десктопе).

## 14. Ветка BPMonitor-Sync: фоновая синхронизация десктоп ↔ bp.xor.world

Десктоп остаётся офлайн-first инструментом; веб — хаб, где данные видны с телефона. Ветвление: отдельная ветка/сборка BPMonitor со слоем синхронизации, **фича включается/выключается галкой в конфиге** (по умолчанию выкл, пока не настроен токен).

**Модель данных.** Обе стороны ведут append-only журнал с Guid'ами записей и монотонным seq — формат это уже позволяет. Синхронизация = обмен дельтами, а не файлами:
- `POST /api/sync/push {sinceSeq, records[]}` — десктоп шлёт записи/тумстоуны, добавленные локально после `sinceSeq`; сервер аппендит, отвечает своим новым seq.
- `GET /api/sync/pull?sinceSeq=` — сервер отдаёт записи, добавленные/изменённые с других устройств (веб-ввод с телефона) после курсора десктопа.
- Курсоры хранятся на обеих сторонах (`data/sync.json`: lastPushedSeq, lastPulledSeq).
- **Конфликты**: правка одной записи с двух мест — last-writer-wins по моменту применения на сервере (сервер — арбитр, у него seq). Для дневника АД это приемлемо: одновременное редактирование одной записи двух устройств — экзотика.
- Удаление = тумстоун по Guid, репликацией тумстоуна merge завершается.

**Транспорт/безопасность.** HTTPS на bp.xor.world; авторизация — **персональный API-токен** (длинный случайный, генерируется в веб-настройках «Устройства», показывается один раз, храним в config.json десктопа 0600-правами по смыслу; отзыв — кнопкой). Токен ≠ пароль: утечка токена не даёт пароль от почты, и токен можно отозвать.

**Фоновый режим в десктопе.** Таймер (интервал в настройках, по умолчанию 15 мин + сразу после локальной записи + при старте): если сеть есть и галка «синхронизация» стоит — push/pull дельты. Сеть пропала — тихо копим, следующий цикл догонит (дельта по seq это делает тривиально). Балюн-индикатор только при ошибке авторизации/конфликте формата, не при каждой синхронизации (не спамим).

**Порядок применения на сервере**: входящие с десктопа записи проходят те же пайплайны, что веб-ввод (Snapshot/FillWx для старых дат, Train, MaybePopup) — данные из офлайна не должны быть «сортами второго сорта».

**Нюансы:**
- Часы десктопа: доверие к timestamps клиента ограничено — порядок merge по серверному seq, timestamp только для отображения.
- Медикаменты/конфиг: конфиг синхронизируется **односторонне веб→десктоп или десктоп→веб** (выбирается «главная» сторона в настройках), двухсторонний merge конфига — слишком хрупкий для v1.
- Первая синхронизация с пустым сервером = автоматический «первый импорт» (тот же пайплайн, что export/all, но построчно через push).
